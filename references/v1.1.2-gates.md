# 执行批准与当前修订要求（V1.1.3）

本页定义 V1.1.2 执行批准及 V1.1.3 修订要求规则；运行时为 [contracts.mjs](../scripts/contracts.mjs) 和 [router.mjs](../scripts/router.mjs)。保留纯函数、七阶段、schema 2 与原顶层状态结构，不接 MCP 或状态后端。

## 迁移项目的执行批准

只要状态保留 migration_record，每个要执行的完整包都必须有当前执行批准；不限于迁移后的首次尝试，后续版本和 reopen 后的新生命周期也不能使用旧批准。

1. 缺批准的 prepare 返回 `PLAN / reauthorization_required`，原 active_packet 不变，不生成执行资格。
2. Chat 在 PLAN 调用 `reauthorize`，提交当前完整拟议 packet 和 approval。没有新用户授权时停止；已有明确授权仍可作为真实来源由 Chat 核对记录，不因工具规则机械地重复询问用户。
3. 批准记录存入 plan_approvals，kind=execution；仅是批准，不运行任务。
4. prepare 发布精确匹配的包，start 再核对批准与实际预检。submit、accept、checkSideEffect 也检查批准，不能从旧运行快照直接跳过门禁。

approval 必需字段：

| 字段 | 规则 |
|---|---|
| reviewer | 只能 CHAT |
| source_kind / approval_ref | user_instruction 或 user_delegation，以及真实可审计来源 |
| approval_id | 非空、在保留的执行批准记录中唯一 |
| project_id / task_id / packet_id / packet_revision / decision_version / executor / lifecycle | 必须与当前拟议包完全相同 |
| from_packet_sha256 | 当前 active_packet.content_sha256；没有活动包才是 null |
| to_packet_sha256 | 完整拟议 Execution Packet 的稳定摘要，包括 scope、executor、side_effects、授权和所有其他包字段 |
| replaces_review_id | 没有替换 Review 来源要求时为 null；兼容原审核引用 |
| replaces_requirement_id | 需要替换/取消当前规划要求时，明确引用 currentRevisionRequirement 的 id；不替换时省略 |

状态额外记录 kind、state_revision 和 revision_instructions。批准自身在包外，避免完整包摘要自引用。`authorization.status=granted` 仍是必要条件，但不足以授权迁移项目；replan 记录也不能冒充 kind=execution。

完整包任一字段改变都使批准失效，包括升至 packet N+1。采用精确绑定，未实现同范围自动续批。下一 prepare 会要求在 PLAN 重新批准；版本规则仍要求 packet_revision 连续加一。副作用只检查具体允许目标，不执行真实动作。

示例：[reauthorize-request.json](../examples/reauthorize-request.json)。所有示例为合成数据，不能作为真实用户批准。

## 当前有效的修订要求

`currentRevisionRequirement(snapshot)` 返回 `{id, source, lifecycle, instructions}` 或 null；`currentRevisionInstructions` 返回同一要求的内容。来源统一读取已有的 revision_reviews、plan_approvals 和 migration_record，不另建一套可漂移的状态。

- REVISE 来源的 id 为 `review:<review_id>`；ESCALATE 来源为 `review-esc:<原始审核稳定摘要>`，source 同为 review。
- 规划/执行批准来源的 id 为 `plan:<批准记录稳定摘要>`。同内容的后续批准不自动替换原要求。
- 迁移来源的 id 为 `migration:<source_sha256>`，只在对应生命周期有效。

replan/reauthorize 可以首次建立要求，无需先进入 REVISE。未记录来源的非空 revision_instructions 不能通过 prepare 悄悄发布，会返回 PLAN 要求 Chat 记录批准。

prepare 每次比较当前要求，连续调用不能清空、替换或追加；合法替换必须在 PLAN 由 Chat 批准完整拟议包，并引用当前要求。规划来源用 replaces_requirement_id；直接替换 Review 来源仍兼容原 replaces_review_id，两个字段不同时使用。取消要求以明确批准的空数组表达，保留取消记录；之后不能未经批准重新添加旧要求。

新的 REVIEW → REVISE 必须引用当前要求。supersedes_review_id 继续记录之前的 REVISE 审核链；当前要求来自规划或迁移时另提供 supersedes_requirement_id。旧要求来源和批准全部保留。迁移待办要求保持原有保护：在新的当前生命周期 Review 核验前，规划批准不能直接撤销它。

当前生命周期的 ACCEPT 是明确完成事件：在核对真实结果和全部验收后，要求不再 active，历史记录保留。reopen 增加生命周期，旧要求不污染新任务；同一生命周期内省略字段不算完成。

## V1.1.3：ESCALATE 累加和持续保存

合法 ESCALATE 的非空 revision_instructions 进入现有 revision_reviews；空数组不取消或替换现有要求。保存的 Review 保留原始意见、审核证据和完整任务身份；路由器额外派生 inherited_requirement（当前 ActiveRevisionRequirement 或 null），记录新增前的有效来源和意见。原始 Review 输入不能自填该字段，review_record 保持原始审核内容。

currentRevisionRequirement 将继承意见和本次新增意见按原顺序合并、去重，使用本次 review-esc:<原始审核稳定摘要> 身份；旧来源记录全部保留。摘要绑定当前项目、任务、包、lifecycle、结果及审核内容，避免新生命周期重用 review_id 时误用旧引用。不解析自然语言等价关系。既有 R1 与新增 R-ESC 都必须携带，不能把新增理解为默认替换。Challenge 的 resolution_ref 只解除阻塞；prepare 独立核对全部有效要求。

显式替换或取消仍使用现有 replan/reauthorize 的完整包批准和当前 requirement 引用；ESCALATE 用 replaces_requirement_id 填写查询返回的完整 id，不用 replaces_review_id 拼接。后续 REVISE 的 supersedes_review_id 指向上一条 REVISE（没有则 null），supersedes_requirement_id 指向当前有效要求，两条引用职责独立。迁移待办经过 ESCALATE 继承后，仍须实际 REVISE 核验，不能靠 ESCALATE 或普通规划批准撤销。

revisionReviews 是共享的保留规则：新 ESCALATE 当次保存；旧 V1.1.2 快照若仍保有当前 ESCALATE review_record，查询即生效，并在下一次成功转换中保留到同一历史集合。prepare 清空 review_record 前已经保存证据。拒绝调用不改传入快照。已经在旧版丢失、且外部也没有保留的审核内容无法凭空恢复；此时需从真实历史证据重新核对。

旧版可能允许当前 ESCALATE 复用先前 REVISE 的 review_id。保留判断比较完整原始审核内容，不能只比较 ID；原始 review_id 与证据保持不变。ESCALATE 的 review-esc: 身份与既有 review: 身份分开，避免任意 review_id 文本构造出旧取消批准的目标。处置时使用查询返回的完整 id。新 Review 事件继续拒绝复用已保留的 review_id；REVISE 审核链的既有 ID 含义不变。

没有新增状态顶层字段或第二套要求日志；已有 schema 2 快照可读取。保存的 ESCALATE 历史含新增派生上下文，旧运行时不能解释这一扩展，写入 V1.1.3 状态后不得降级至旧运行时继续执行。

| 合法入口 | 建立和持续读取 | 明确处置 | 生命周期 |
|---|---|---|---|
| REVISE | 原始审核写入 revision_reviews，当前 review 身份供 prepare 比较 | 引用当前要求的 REVISE 或完整包规划批准 | ACCEPT 完成；reopen 隔离 |
| replan | plan_approvals 的已批准意见形成 plan 身份 | 正确 requirement 引用、Chat 可信来源、完整包摘要 | 同上 |
| reauthorize | 同一 plan_approvals 机制，同时具备迁移执行批准身份 | 同上，且仍满足执行批准契约 | 同上；新执行包重新批准 |
| migration | migration_record.pending_revision_instructions 形成 migration 身份 | 须经当前 lifecycle 的实际 REVISE 核验；不能由普通规划批准直接撤销 | 仅 target_lifecycle 生效 |
| ESCALATE | revision_reviews 保存原始审核及 inherited_requirement，合并当前意见 | 引用合并后的当前身份；迁移继承限制保持 | ACCEPT 完成；reopen 隔离 |

## 已有 V1.1.1 状态

已有字段和旧 replan/Review 记录可读取，原 replaces_review_id、supersedes_review_id 的历史含义保留。新增字段是对新事件的显式扩展，缺字段不会默认获得执行批准。

没有 lifecycle 的 schema 1 / 旧 schema 2 仍按 [七状态迁移](migration-v1.1.md) 处理。已有 lifecycle 的 V1.1.1 状态禁止再次迁移重置版本。其迁移项目若缺少新批准，旧 READY/EXECUTE 不得 start、submit 或执行副作用，旧 REVIEW 不得直接 accept；可通过原有 Challenge/REVISE 路径回到 PLAN，在新包取得批准后继续。缺批准的旧 COMPLETE 不符合新 COMPLETE 契约，只保留为历史证据，不能直接作为新版本有效完成状态使用。

批准来源真实性、权威快照不可篡改性和并发保存仍由可信宿主/人工负责；JSON 身份和哈希提供一致性约束，不是身份认证或工具执行沙箱。
